How to use this tool

Work down the page. Each numbered section feeds the next, and everything recalculates as you type. Nothing is sent anywhere and nothing is saved unless you press Save file, so experiment freely and use Undo when an experiment goes wrong.

  1. Set what the programme is worth at launch. Either build it from the commercial model - patients, price, margin, patent life - or type a single figure if your commercial team already has one. This is the prize every later number is a share of, so start here.
  2. Enter your questions. One row per experiment or study you must pass before the programme continues. Give each a probability of success, a cost in EUR M and a duration in months, and put your intended running order in the "Your order" column. Add and remove rows as needed.
  3. Describe the stages that follow. The trials and reviews the questions are gating. Their durations also decide how much patent life is left to sell into, so they affect the value at launch.
  4. Read the answer. The tool returns the cheapest running order, the best mix of parallel and sequential work, and what each is worth against the order you intended. Set precedence rules and a capacity limit in step 2 if some questions cannot start until others finish.
  5. Check it against your plan, then take it away. Enter your budgeted totals so the totals row flags any drift, look at the charts to see when money is spent and when value appears, then Save file to keep the configuration or Export CSV to put the numbers in a spreadsheet.

New here? Press Load example in step 2 to fill the tool with a worked case, change one number at a time, and watch what moves. Note that the commercial model is a simplification and books no revenue after patent expiry, so the value at launch is a floor rather than a central estimate.

Why order matters at all

Order changes neither the value at launch nor the chance of getting there, because multiplying the probabilities together gives the same answer whatever sequence you use. It changes only how much money you spend before a failure stops the programme, and when you spend it. So the change in programme value is exactly the change in the present value of expected spend, with the sign flipped, and the whole question lives in the cost domain: run questions in ascending cost / (1 - PoS) when timing is free, and ascending cost / (1 - PoS x e^(-rate x duration)) once a slow question delays everything behind it. The identity below holds to machine precision; it breaks only when the programme is worth abandoning at some gate, because then part of the spend is never incurred at all.
